
一、 游戏核心定位：工程级实现策略
单场景加载（无缝感）：在Unity的Build Settings中，将“启动/账户选择”作为场景0（主场景），后续章节和小游戏作为场景1、2、3。运行时采用 “基座常驻 + 附加场景动态叠加” 的策略，玩家只会在基座上看到场景的淡入淡出。
无联网保障：在Package Manager中彻底移除所有网络相关模块（如Unity Networking、WebGL相关的JS插件），防止引擎底层发起任何网络请求。
轻量化前置：项目创建时选择2D/3D最小模板，剔除不必要的引擎默认资源（如Standard Assets）。
二、 整体架构（三层核心）实现方法
目录物理隔离：在Project窗口中，严格建立 Core（底层）、Logic（逻辑层）、Presentation（表现层）三个顶层文件夹。通过Unity的Assembly Definition（程序集定义，.asmdef）为这三层分别创建独立的编译单元。
依赖方向控制：利用Assembly Definition的引用设置，强制规定：表现层可引用逻辑层，逻辑层可引用底层，但严禁反向引用。编译器层面直接阻断违规调用。
层间通信：弃用Unity传统的拖拽绑定（GetComponent），采用C#原生事件委托或轻量级事件总线，实现表现层与逻辑层的解耦。
三、 多账户管理体系实现方法
存储路径获取：使用Unity提供的 Application.persistentDataPath 获取各平台（PC、Mac等）标准的用户可读写数据目录。在此目录下通过C#的 Directory.CreateDirectory 动态生成 Saves/ 文件夹。
数据序列化：账户数据模型设计为纯C#类（不继承MonoBehaviour），打上序列化标签。利用Unity原生的 JsonUtility 进行对象与JSON字符串的互转，结合 File.WriteAllText / ReadAllText 完成磁盘读写。
多存档位映射：采用约定大于配置的方式，硬编码三个存档位标识（如1、2、3），与文件名 Slot_1.json 等直接映射。
四、 数据完全隔离机制（关键）实现方法
文件隔离（纯静态工具类）：将所有文件读写操作封装在一个无状态的纯静态工具类中。该类不包含任何成员变量，只提供接收参数和返回数据的纯函数，从设计模式上杜绝文件缓存导致的数据串扰。
内存隔离（唯一数据源）：整个游戏中，只允许一个单例管理器持有当前账户的数据对象实例。其他所有脚本（UI、小游戏、剧情）需要数据时，只能通过该单例提供的 只读属性（Getter） 进行访问，禁止拿到对象的引用进行修改。修改操作必须通过单例暴露的特定方法（如“完成小游戏”）进行。
逻辑隔离（节点黑盒机制）：每个章节脚本和小游戏脚本在启动时，只向GameManager询问“我该干什么”，而不去问“其他章节干了什么”。
切换账户流程（协同程序串联）：
调用保存接口，将当前数据写入磁盘。
遍历Unity的 SceneManager.sceneCount，通过名称比对，异步卸载所有非基座场景（UnloadSceneAsync）。
在卸载完成的回调中，将GameManager中的数据引用置为 null。
调用 Resources.UnloadUnusedAssets() 卸载非引用资源。
强制调用系统级垃圾回收 GC.Collect()。
激活账户选择UI界面。
五、 内存分配与管理实现方法
常驻内存管控：只对挂载GameManager的初始GameObject使用 DontDestroyOnLoad。严格审查此对象上挂载的脚本，确保只有极其轻量的逻辑代码，绝对不挂载任何UI组件、大体积资源引用或音频源。
场景内存管控：
加载：永远使用 LoadSceneAsync 且模式设为 Additive（附加加载），避免基座场景被销毁导致管理器丢失。
卸载：章节过渡或小游戏结束时，精准指定场景名进行异步卸载。
小游戏内存“用完即焚”：
小游戏运行中产生的临时特效、生成的动态对象，全部通过对象池管理或在小游戏结束时执行 Destroy。
小游戏场景卸载后，确保没有任何MonoBehaviour在 OnDestroy 之外的地方还保留着对小游戏内GameObject或组件的引用（这会导致Unity无法释放内存）。
资源加载防泄漏：如果使用 Resources.Load 或 AssetBundle 加载资源，必须遵循“谁加载谁负责卸载”的原则，绝不把加载出来的资源（如Sprite、AudioClip）直接赋值给全局静态变量。
六、 全局核心管理器实现方法
单例模式加固：采用“懒汉式+防重复创建”的单例模式。在 Awake 中判断如果实例已存在，则直接 Destroy 自身，确保场景切换或误操作时全局绝对唯一。
生命周期免疫：由于使用了 DontDestroyOnLoad，该管理器不受Unity场景加载/卸载的生命周期影响。因此，严禁在此管理器中使用 Start 或 Update 去处理与特定章节相关的业务逻辑。
状态机控制流：在GameManager内部实现一个极简的枚举状态机（如：账户选择、剧情播放中、小游戏中、场景切换中）。所有的外部请求（如点击返回主菜单）必须先校验当前状态，防止在“场景切换中”进行“保存数据”导致逻辑崩溃。
七、 游戏完整运行流程的Unity生命周期映射
启动流程：Unity加载初始场景 -> 唤醒GameManager单例 -> 触发UI管理器拉取本地JSON文件列表 -> 渲染三个存档位的UI状态（空/有存档/时间）。
游戏内流程：玩家点击开始 -> GameManager记录激活槽位 -> 异步附加加载章节场景 -> 场景激活后触发剧情组件 -> 剧情中途通过消息机制启动小游戏附加场景 -> 小游戏结束发送完成信号 -> 触发GameManager保存逻辑 -> 卸载小游戏场景。
退出游戏：监听Unity底层的 OnApplicationQuit 消息，在此处插入最后一次强制保存逻辑，确保即便是杀进程也能保底存档。
八、 补充：低配电脑适配的工程规范
渲染层极简：弃用Unity默认的标准渲染管线，改用 URP (通用渲染管线)，并关闭所有后处理（抗锯齿、泛光、景深）。甚至对于纯2D科普游戏，直接使用Built-in管线配合Sprite Renderer即可。
DrawCall控制：强制美术规范，所有散图必须打入图集。确保同一个章节场景内的所有UI和2D元素，DrawCall总数不超过50。
物理与动画降级：禁用不必要的物理碰撞（Rigidbody2D），使用纯数学插值代替物理引擎模拟。动画尽量使用帧动画或Tween补间动画，减少Animator状态机的复杂度和骨骼动画的计算开销。
帧率与画质硬锁：在游戏初始化的第一帧，通过脚本强制调用 QualitySettings.SetQualityLevel(0) 锁定最低画质，并使用 Application.targetFrameRate = 30 限制帧率，降低低端CPU和显卡的发热与负载。
